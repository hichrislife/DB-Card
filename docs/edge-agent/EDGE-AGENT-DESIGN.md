# 地端智能體架構設計（Edge Agent Design）

> 適用硬體：13 代 i7 等級 CPU（約 16 核 / 24 執行緒）、64GB RAM、1TB SSD、RTX 5070 Ti（16GB GDDR7）、DeepX DX-M1 NPU（M.2 2280，25 TOPS INT8，4GB LPDDR5）。
> 部署型態：同一套系統，以設定檔切換「公務機關（受管制）」與「一般（企業／個人）」兩種路徑，見第 2.5 節。
> 設計目標：地端用戶可透過多工協調調動模組、自行修改模組；在離線環境下以隨身碟把「地端聽不懂的案例」帶到雲端版調整，再把更新帶回地端；所有輸出可追溯依據、無法核實即標示，不產生無依據的幻覺。

本文件與 DB-Card 專案本身的程式碼無關，是一份獨立的系統設計書。延續 DB-Card「隱私優先、資料不出本機」的精神，這套架構預設**地端完全離線可用**，雲端只是選配的「老師」。

## 0. 先講清楚三件事（避免後面設計走偏）

1. **「動態調整權重」不等於每次對話都改模型權重。**
   在 16GB VRAM 上即時訓練是不切實際的，也沒有必要。真正有效的做法是把「貼近用戶情境」拆成四層，依速度排序：
   提示與路由設定（秒級）→ 記憶與術語庫（分鐘級）→ LoRA 轉接器熱切換（秒級切換、小時級訓練）→ 基底模型（幾乎不動）。
   用戶 95% 的「聽不懂」問題，是**術語、縮寫、單位內部用法、文件找不到**，這些靠術語庫與檢索就能解決，不需要動權重。

2. **「無幻覺」在工程上的可達成版本是「每一句主張都可追溯，追溯不到就標示並拒答」。**
   沒有任何模型能保證零幻覺；能保證的是：輸出中每一個事實性主張都附有來源片段編號，並由獨立的核實模型做蘊含檢查，不通過就刪除或標示「無法核實」。這份設計把這件事做成硬性閘門，不是提示詞請求。

3. **雲端版不一定是公有雲。**
   你的情境若涉及公務或敏感資料，「雲端版」可以是機關內部有大 GPU 的伺服器。隨身碟流程對兩者都適用；差別只在雲端那一側用什麼老師模型。

## 1. 硬體角色分工

4GB 卡是 DeepX DX-M1，這改變了分工：DX-M1 是第一代視覺導向 NPU，INT8 運算，官方 SDK 明列支援的是 YOLO、ViT、VLM 一類模型；BERT 類文字編碼器與 Whisper 沒有公開證實支援，LLM 則要等尚未出貨的 DX-M2。因此 **DX-M1 不承接嵌入、重排、NLI 核實與語音轉文字**，這些小模型放主卡或 CPU，DX-M1 專責它擅長的影像任務。DX-M1 的整合細節見附錄 A。

| 元件 | 角色 | 載入內容 | 預估佔用 |
|---|---|---|---|
| RTX 5070 Ti 16GB | 主推論 + 小模型 | 主 LLM（4-bit 量化 8B）+ KV 快取 + 1～3 個 LoRA + 嵌入／重排／NLI（fp16） | LLM 約 5GB，KV 約 4GB（32K 上下文），小模型約 2.8GB，合計約 12GB |
| DeepX DX-M1（4GB） | 視覺 | 文件版面分析、OCR 文字偵測、表格與印章偵測、影像／證件去識別化、攝影機或 kiosk 影像分析 | INT8 視覺模型多在數十 MB 等級，4GB 足夠同時常駐 5 個以上 |
| CPU + 64GB RAM | 協調與資料層、備援推論 | 協調器、任務佇列、向量庫、全文索引、文件解析、規則引擎、評測；小模型的 CPU 備援（ONNX Runtime INT8） | 預留 16GB 給 LLM 溢出時的 CPU 卸載 |
| 1TB SSD | 儲存 | 模型檔（約 60GB）、文件庫與索引、互動日誌、轉接器版本庫、評測集 | 建議模型與資料各分一個分割區 |

### 1.1 小模型放哪裡：兩種配置

| 配置 | 主 LLM | 嵌入／重排／NLI 位置 | 適用 |
|---|---|---|---|
| A：主卡共用（預設） | 8B 4-bit（約 5GB） | 主卡 fp16，約 2.8GB | 延遲最低；16GB 放得下 LLM + KV + 小模型 |
| B：CPU 承接 | 14B 4-bit（約 9GB） | CPU，ONNX Runtime INT8，24 執行緒 | 想用 14B 時主卡放不下小模型；嵌入約每秒 20～60 片段，NLI 每句約 30～80 毫秒，互動仍可接受 |

兩種配置都寫在部署設定檔裡（第 2.5 節），切換不用改程式。

### 1.2 NPU 的使用原則

- **先驗證再上線**：任何要搬到 NPU 的模型，用同一批資料跑 fp16 參考版本與 NPU 版本，嵌入模型比對檢索前 10 名重疊率（應 ≥ 0.9），NLI 比對判定一致率（應 ≥ 0.97），不達標就留在主卡或 CPU。
- **NPU 走獨立服務**：用廠商 SDK 包成一個 gRPC／HTTP 服務，協調器只透過 MCP 工具呼叫（例如 `vision.layout`、`vision.ocr_detect`、`vision.redact_faces`），NPU 故障時這些工具回報不可用，LLM 主流程不受影響。
- **把文件前處理交給它**：掃描件與 PDF 的版面分析、表格框線偵測、印章與簽名區域偵測，這些是 NPU 的強項，能把文件切塊品質拉高，間接提升檢索與核實的準確度。
- **語音不上 DX-M1**：用 CPU 跑 faster-whisper small INT8（約 2～3 倍實時速度），語音活動偵測用 Silero VAD（CPU）。若日後 DX 模型庫出現 Whisper 編碼器，再依第一點的驗證流程評估。

**主模型選擇**（都以 4-bit 量化計）：

| 候選 | 體積 | 中文能力 | 適合情境 |
|---|---|---|---|
| Llama-3.1-TAIDE-LX-8B / Llama-Breeze2-8B | 約 5GB | 繁中、台灣用語佳 | **公務機關設定檔預設**；有「不得使用特定來源軟體」政策時的首選 |
| Gemma 3 12B（QAT） | 約 8GB | 多語佳 | 需要影像輸入時 |
| Qwen3-14B | 約 9GB | 推理與工具呼叫強 | 一般企業情境；公務機關需先確認採購與資安政策是否允許 |
| Qwen3-30B-A3B（MoE） | 約 18GB，需 CPU 卸載 | 強 | 想要更高品質且能接受每秒約 15～25 token |

建議：**基底模型選定後就不要頻繁換**，因為所有 LoRA 轉接器、評測基準、提示詞都綁定基底。兩種設定檔都先用 8B 等級把整條流程跑通（配置 A），一般設定檔再評估是否升到 14B（配置 B）。

## 2.5 兩條部署路徑：公務機關設定檔與一般設定檔

同一套程式、同一套模組登錄庫、同一種隨身碟包格式；差異全部收在一個設定檔裡（範例見 `examples/profile.gov.yaml` 與 `examples/profile.general.yaml`）。安裝時選一個，之後可改，但改基底模型要重跑所有評測。

| 面向 | 公務機關設定檔 `gov` | 一般設定檔 `general` |
|---|---|---|
| 基底模型候選 | TAIDE-LX-8B、Breeze2-8B、Gemma 3、Llama 3.1；排除政策不允許來源的模型 | 不限，預設 Qwen3-8B／14B |
| 雲端老師 | 機關內部 GPU 伺服器或經核定的政府雲端環境，跑 70B 等級開源模型；**不使用公有 LLM API** | 公有雲 Claude Opus 5.5（`claude-opus-5-5`）走 Message Batches；或自建 |
| 匯出內容 | 只匯出事件、術語、評測集、模組設定；**永不匯出文件原文**；機密等級以上事件一律不匯出 | 可匯出文件片段原文，經個資遮蔽後；分級由管理者設定 |
| 網路 | 地端節點完全離線，只靠隨身碟 | 允許選配線上同步，隨身碟為備援 |
| 模組修改權限 | `low` 風險模組一般用戶可改；`high` 需資安或主管核准，並留存核准紀錄 | `high` 需管理者核准 |
| 輸出揭露 | 每份輸出附「由生成式 AI 協助產出，已附來源，請人工覆核」字樣 | 可關閉 |
| 稽核日誌保存 | 依機關文書與資安規範，預設 5 年、不可竄改（append-only + 雜湊鏈） | 預設 1 年 |
| 使用規範依據 | 以行政院及所屬機關使用生成式 AI 參考指引及機關自訂資安規範的最新版為準 | 企業內規 |

兩條路徑在「核實閘門」上**沒有差異**：拒答門檻、蘊含門檻、更新包閘門規則完全相同。放寬核實標準不是任何設定檔的選項。

**「有跟沒有都做」的實作方式**：

1. 程式碼只認 `profile.yaml` 裡的欄位，不寫死任何機關或公司名稱。
2. CI 對兩個設定檔各跑一次完整流程（匯入文件 → 問答 → 核實 → 匯出 → 模擬雲端處理 → 匯入更新 → 閘門），兩邊都要綠燈才算一個版本完成。
3. 雲端老師那一側抽象成一個介面（`Teacher`），有兩個實作：`OnPremTeacher`（開源大模型）與 `ClaudeTeacher`（Anthropic API），輸出同樣的更新包格式。
4. 隨身碟包的 `manifest.json` 帶 `profile` 欄位，地端匯入器拒絕與自己設定檔不符的更新包（例如 `general` 老師產的包不能進 `gov` 節點）。


## 3. 多工協調：用戶怎麼「調動模組」

### 3.1 模組的定義

一個模組不是一段寫死的程式，而是一個資料夾，用戶看得懂也改得動：

```
modules/
└── 公文摘要/
    ├── manifest.yaml      # 名稱、說明、觸發條件、輸入輸出、風險等級、需要哪些工具
    ├── prompt.md          # 系統提示詞（用戶可改）
    ├── tools/             # MCP server（可選，提供工具給 Executor 呼叫）
    ├── evals/cases.jsonl  # 這個模組的驗收案例（改完模組要跑過才生效）
    └── adapter: 公文風格-v3   # 指向轉接器庫中的 LoRA（可選）
```

`manifest.yaml` 範例見 `examples/module.example.yaml`。重點欄位：

- `triggers`：自然語言描述 + 關鍵詞。協調器把所有模組的描述做向量嵌入，用戶的輸入先和模組描述比對，選出候選模組。
- `inputs` / `outputs`：用 JSON Schema 描述，讓模組之間可以串接，也讓輸出可以用受限解碼（grammar）強制符合格式。
- `requires.tools`：列出要呼叫的 MCP 工具名稱，協調器啟動時檢查是否可用。
- `grounding.required: true`：此模組的輸出必須通過核實閘門（第 5 節）。
- `risk_level`：`low` 可由任何用戶修改；`high`（例如會寫入資料庫、寄信）修改後需管理者核准才上線。

**為什麼用 MCP 當模組介面**：它是目前地端與雲端工具生態的共同協定，用戶在雲端版調好的工具可以原封不動搬到地端；反之亦然。

### 3.2 三種調動方式

| 方式 | 適合誰 | 作法 |
|---|---|---|
| 自然語言 | 一般用戶 | 直接說「幫我把這份公文摘要成三點再翻成英文」，協調器拆成「公文摘要 → 翻譯」兩個模組串接 |
| 明確指令 | 熟手 | `/公文摘要 --style 簡潔` 直接指定模組與參數，跳過路由 |
| 工作流 YAML | 要重複執行的流程 | 寫一份 `workflow.yaml` 定義模組順序、條件分支、平行執行；存成新模組 |

工作流範例：

```yaml
name: 會議紀錄處理
steps:
  - id: stt
    module: 語音轉文字
    input: { audio: $input.file }
  - id: summary
    module: 會議摘要
    input: { transcript: $stt.text }
  - id: actions
    module: 待辦擷取
    input: { transcript: $stt.text }
    parallel_with: summary          # 與 summary 平行跑
  - id: verify
    module: 核實
    input: { claims: $summary.claims, sources: [$stt.text] }
    required: true                   # 不通過就不輸出
output:
  summary: $summary.text
  todos: $actions.items
  evidence: $verify.report
```

### 3.3 資源排程（讓多工不打架）

- **GPU 槽位**：主卡交給 vLLM 的連續批次處理（continuous batching），同時可服務 4～8 條對話；排程器只控制「同時最多幾個需要長上下文的任務」，避免 KV 快取爆掉。
- **小卡槽位**：嵌入與重排為同步短任務，設一個長度 32 的佇列即可。
- **CPU 池**：文件解析、OCR、索引重建、評測跑分放在低優先序的背景執行緒池，不搶前景對話。
- **優先序**：互動對話 > 核實 > 工具呼叫 > 背景索引 > 評測。
- **LoRA 切換**：vLLM 開啟 `--enable-lora` 並允許執行期載入，同一個基底同時掛多個轉接器，每個請求指定用哪一個；llama.cpp server 則用 `/lora-adapters` 端點調整各轉接器的權重比例。切換成本是毫秒級，這就是「動態」的真正來源。

### 3.4 用戶如何「修改模組成自己需要的東西」

1. 在 UI 按「複製模組」→ 產生 `modules/我的公文摘要/`。
2. 改 `prompt.md`（例如加上自己單位的格式要求）、改 `manifest.yaml` 的觸發詞。
3. 在 `evals/cases.jsonl` 加 3～5 個自己的範例（輸入 + 期望輸出的重點）。
4. 按「驗證並啟用」：系統跑該模組的評測案例，並跑全域的「核實回歸」（確保沒把 grounding 關掉），通過才上線。
5. 所有修改進本機 git，可比對、可回滾。

這個流程設計成**不用寫程式**也能完成 80% 的客製化；要加新工具（MCP server）才需要寫程式。

## 4. 四層「貼近用戶情境」調整堆疊

| 層 | 內容 | 更新速度 | 在哪裡更新 | 風險 |
|---|---|---|---|---|
| L0 基底模型 | 開源 LLM 權重 | 半年～一年 | 雲端挑選，地端整包更換 | 高，所有東西要重測 |
| L1 LoRA 轉接器 | 用戶領域語感、格式習慣、長尾術語的「內化」 | 每週～每月一版 | **雲端訓練**（或地端夜間排程，限 8B 基底） | 中，必須過評測閘門 |
| L2 記憶與術語庫 | 術語表、縮寫對照、用戶修正紀錄、常見問答、文件索引 | 即時 | 地端，用戶可直接編輯 | 低 |
| L3 提示與路由 | 系統提示、輸出格式、模組觸發規則、偏好設定 | 即時 | 地端 | 低 |

**運作原則**：遇到「聽不懂」先從 L3、L2 解；累積到一定量（例如同類失敗 30 筆以上）才值得做成 L1 的訓練資料。這樣既能馬上見效，又不會把雜訊訓進權重。

### 4.1 「聽不懂」事件的定義與捕捉

以下任一條件成立就記錄為一筆 `misunderstanding` 事件，進入匯出佇列：

- 檢索最高分低於門檻（例如重排分數 < 0.35），模型被迫拒答。
- Verifier 判定輸出有主張無法被來源蘊含。
- 用戶按「不是這個意思 / 答錯了」或直接改寫答案。
- 路由把請求送到錯誤模組（用戶手動改選模組）。
- 模型輸出中出現術語庫沒有的專有名詞且上下文中無定義。

每筆事件記錄：用戶輸入、檢索到的片段 ID 與分數、選用模組與轉接器版本、模型輸出、Verifier 判定、用戶回饋。**預設不記錄原始文件內容**，只記錄片段 ID 與雜湊，除非管理者開啟「允許匯出內容」。

### 4.2 LoRA 訓練的現實邊界

- 16GB VRAM 可以做 8B 基底的 QLoRA（4-bit 基底、序列長度 2048、batch 1、gradient checkpointing，約佔 10～12GB），1,000 筆資料約 1～2 小時。
- 14B 基底的 QLoRA 在 16GB 上很勉強，建議交給雲端。
- 轉接器要「小而多」：每個領域或每個單位一個，rank 8～16，檔案數十 MB，隨身碟搬運沒負擔。
- 訓練資料的來源只能是：用戶確認過的修正、雲端老師依據**用戶自己的文件**生成並附有來源的合成問答。不要用老師模型「憑空」生成的知識去訓，否則是把雲端的幻覺搬進地端。

## 5. 核實閘門：如何做到「有依據、可追溯、不幻覺」

### 5.1 生成端的約束

1. **只能引用，不能自由發揮**：Writer 的系統提示要求每個事實性句子結尾附 `[S3]` 之類的片段引用；沒有可引用來源的句子必須改寫成「文件中未提及……」。
2. **受限解碼**：工具呼叫與結構化輸出用 JSON Schema / grammar 強制格式，杜絕格式幻覺。
3. **拒答優先**：檢索分數低於門檻時，直接回「我在現有文件中找不到依據」，並記錄事件，而不是硬答。

### 5.2 核實端（Verifier）的流程

```
Writer 輸出
   │
   ▼
拆句 → 分類（事實性主張 / 非主張如問候、格式）
   │
   ▼ 只對事實性主張
對每個主張：取出它引用的片段 → NLI 模型判定 蘊含 / 中立 / 矛盾
   │
   ├─ 蘊含 ≥ 門檻 → 保留，附來源
   ├─ 中立       → 標示「⚠ 無法由來源確認」，或依模組設定刪除
   └─ 矛盾       → 刪除，並記錄為高優先事件
   │
   ▼
產生 evidence.json（主張、來源、判定、分數）隨答案一起輸出
```

- NLI 模型依配置放在主卡（配置 A，每句約 20～50 毫秒）或 CPU（配置 B，每句約 30～80 毫秒），一段 10 句的回答核實成本都在一秒內。
- 高風險模組（`risk_level: high`）再加一道「雙模型交叉」：用主模型以不同提示重新生成一次，兩次主張不一致者降級為「無法確認」。
- 用戶介面上，每個句子可點開看來源原文，這是讓用戶信任系統的關鍵，也是用戶回報「這個來源不對」的入口。

### 5.3 評測與閘門

- **黃金評測集**（`eval/golden.jsonl`）：由用戶實際問題 + 人工確認答案 + 來源組成，從 50 題起步，每次匯出帶去雲端，每次匯入前拿來跑。
- 指標：**忠實度**（主張被來源蘊含的比例）、**拒答正確率**（無依據時是否拒答）、**路由正確率**、**任務完成率**。
- 閘門規則：任何更新（轉接器、提示、術語庫批次）要上線，忠實度不得下降超過 1 個百分點，且矛盾類判定不得增加。不過就自動退回。

## 6. 隨身碟離線同步（Sneakernet）

### 6.1 匯出包（地端 → 雲端）

```
edge-export-<節點ID>-<日期>/
├── manifest.json            # 格式版本、節點 ID、基底模型與轉接器版本、各檔案 SHA-256、資料分級、簽章
├── events/
│   ├── misunderstanding.jsonl   # 聽不懂事件（第 4.1 節）
│   └── corrections.jsonl        # 用戶修正（原輸出 → 用戶改寫）
├── glossary.yaml            # 目前術語庫（含用戶自己加的）
├── eval/golden.jsonl        # 黃金評測集
├── modules/                 # 用戶修改過的模組（manifest + prompt，不含工具程式碼）
└── index_meta.jsonl         # 文件片段 ID、雜湊、來源檔名（預設不含內容）
```

流程：UI 按「匯出」→ 系統依資料分級過濾（例如「機密」等級事件一律不匯出）→ 整包用 `age` 或 GPG 加密、用節點私鑰簽章 → 寫入隨身碟。範例見 `examples/bundle-export.manifest.example.json`。

### 6.2 雲端老師的處理流程

1. **驗簽、解密、病毒掃描**。
2. **失敗分群**：把事件依向量相似度分群，每群標記一種根因：
   - 術語缺口 → 產出 `glossary.delta.yaml`
   - 檢索缺口（文件有但沒找到）→ 調整切塊策略或產出查詢改寫規則
   - 路由錯誤 → 修改模組 `triggers`
   - 推理或語感缺口 → 才進入 LoRA 訓練資料
3. **產生訓練對**：老師模型依據用戶文件片段（若有匯出）生成問答，每一筆都必須附來源片段 ID，無來源者丟棄。
4. **QLoRA 訓練**：與地端同一基底，輸出 `adapter_model.safetensors` + `adapter_config.json`。
5. **回歸評測**：用匯出包帶來的黃金集跑一次，附 `eval/report.json`。
6. **打包、簽章**。

老師模型由設定檔決定（第 2.5 節）：
- `general`：Claude Opus 5.5（`claude-opus-5-5`）做分群、根因診斷與合成問答生成；批次工作走 Message Batches 端點可省一半費用；用結構化輸出（`output_config.format`）讓每筆合成問答都帶 `source_chunk_id` 欄位，方便過濾無來源資料。
- `gov`：機關內部 GPU 伺服器或經核定的政府雲端環境，跑 70B 等級開源模型做同樣的事；流程、輸出格式、閘門完全相同。

### 6.3 更新包（雲端 → 地端）

```
edge-update-v<版本>/
├── manifest.json            # 目標基底模型版本、相容的地端最低版本、各檔案雜湊、雲端簽章、變更摘要
├── adapters/
│   └── 公文風格-v4/
│       ├── adapter_config.json
│       └── adapter_model.safetensors
├── glossary.delta.yaml      # 術語增量（新增 / 修改 / 刪除）
├── router.rules.yaml        # 模組觸發規則調整
├── prompts/                 # 建議的提示詞修改（以差異形式）
├── eval/report.json         # 雲端跑過的回歸結果
└── CHANGELOG.md             # 給用戶看的白話說明：這次解決了哪幾類聽不懂
```

### 6.4 地端匯入閘門（最重要的一段）

```
插入隨身碟
  → 驗簽（只接受已登錄的雲端公鑰）
  → 檢查 manifest 的基底模型版本與地端一致，否則拒絕
  → 病毒掃描、檔案雜湊比對
  → 放入 staging/，不直接覆蓋
  → 用地端黃金集重跑評測（不信任雲端帶來的 report，自己再跑一次）
  → 通過閘門規則（第 5.3 節）
  → 金絲雀：先只對 10% 請求或「影子模式」（新舊並跑、只記錄不輸出）啟用 24 小時
  → 比較金絲雀期間的 Verifier 矛盾率、用戶修正率
  → 升級為正式版；舊版保留至少兩代可一鍵回滾
```

每一步都寫入稽核日誌。匯入失敗的更新包不刪，留在 `quarantine/` 供管理者檢視。

### 6.5 安全要點

- 隨身碟專用：只接受特定格式、特定目錄結構，忽略其他檔案；自動執行一律關閉。
- 雙向簽章：地端節點與雲端各自持有金鑰，對方公鑰在部署時人工登錄。
- 資料分級在匯出端強制執行，而不是靠雲端自律。
- 轉接器檔案只接受 safetensors 格式（不會執行任意程式碼），拒絕 pickle 類格式。

## 9. 已知限制與取捨

- **DX-M1 只給視覺任務**。要把嵌入、NLI 或 Whisper 搬上去，前提是 DX 模型庫或 DX-COM 能編譯對應模型，且通過第 1.2 節的精度比對；目前公開資料沒有證實這一點。
- **DX-M1 的 SDK 文件（developer.deepx.ai、docs.radxa.com）在本次撰寫環境無法存取**，附錄 A 的規格來自 DeepX 公開型錄與經銷商頁面，模型庫清單請在部署前以實際安裝的 SDK 版本為準。
- 配置 A 把小模型放主卡，會把主 LLM 限制在 8B 等級；要用 14B 就要接受配置 B 的 CPU 延遲。
- 16GB 主卡同時掛多個 LoRA 會吃掉約每個 100～300MB 的 VRAM，建議同時常駐不超過 4 個。
- 32K 以上上下文會明顯壓縮可並行的對話數；長文件走「先檢索再回答」，不要整份塞進上下文。
- 隨身碟往返通常以週為單位，L1 轉接器的更新節奏天生較慢；設計上已把能即時解決的問題放在 L2、L3。
- 這份設計沒有處理多台地端節點之間的衝突合併；若未來有多節點，術語庫與模組需加上來源節點與時間戳做三方合併。

## 附錄 A：DeepX DX-M1 整合說明

### A.1 規格（依 DeepX 公開型錄與經銷商資料）

| 項目 | 數值 |
|---|---|
| 運算 | 25 TOPS（INT8） |
| 記憶體 | 4GB LPDDR5，另有 QSPI NAND |
| 介面 | M.2 2280 M-key，PCIe Gen3 x4 |
| 功耗 | 典型 3W，最大 5W |
| 主機 | x86 與 ARM，Linux |
| 製程 | Samsung 5nm |

### A.2 SDK 組成與工作流

| 元件 | 用途 |
|---|---|
| DX-COM | 編譯器：ONNX（搭配量化設定檔）→ `.dxnn`。PyTorch、TensorFlow、Keras 模型須先轉 ONNX |
| DX-RT | 執行期，C++ 與 Python API；本設計用它包成 gRPC 服務 |
| DX-STREAM | GStreamer 外掛，攝影機與影片串流推論 |
| DX-APP | 範例應用 |
| DX-Model Zoo | 預編譯模型庫 |

工作流：選模型 → 匯出 ONNX → 準備校正資料集（INT8 量化用，建議 200～500 張自己場域的影像）→ DX-COM 編譯 → 用第 1.2 節的方法比對精度 → 部署到 DX-RT 服務。

### A.3 本設計分配給 DX-M1 的模型

| MCP 工具 | 模型類型 | 用途 | 備註 |
|---|---|---|---|
| `vision.layout` | 版面分析（YOLO 系列，訓練於 DocLayNet／PubLayNet 類資料） | 把掃描件與 PDF 頁面切成標題、段落、表格、圖、頁首頁尾 | 直接提升文件切塊品質，是對 RAG 幫助最大的一項 |
| `vision.ocr_detect` | 文字區域偵測（DBNet／YOLO 類） | 找出文字框，辨識交給 CPU 的 OCR 辨識模型 | DX-M1 只做偵測，辨識（序列模型）留在 CPU |
| `vision.table_seal` | 表格框線、印章、簽名、手寫區偵測（YOLO） | 公文與表單的欄位定位、印章存在性檢查 | 公務情境常用 |
| `vision.redact_faces` | 人臉與證件偵測（YOLO） | 影像匯入前去識別化，匯出包絕不帶可辨識人像 | 與 `gov` 設定檔的匯出政策配合 |
| `vision.kiosk` | 人員偵測、姿態、物件（YOLO／ViT） | kiosk 或攝影機場景的即時分析 | 走 DX-STREAM |

### A.4 明確不放在 DX-M1 的項目

| 項目 | 原因 | 放哪裡 |
|---|---|---|
| 文字嵌入（bge-m3） | BERT 類文字編碼器未見於官方支援清單；INT8 量化對檢索品質影響需另驗 | 主卡（配置 A）或 CPU（配置 B） |
| 重排序（bge-reranker） | 同上 | 同上 |
| NLI 核實（mDeBERTa） | 同上，且核實是閘門，不接受精度折損 | 同上 |
| Whisper | 未見於官方支援清單 | CPU（faster-whisper INT8） |
| 任何 LLM | DX-M1 非 LLM 設計，LLM 導向的 DX-M2 尚未出貨 | 主卡 |

### A.5 服務介面

```
npu-service (DX-RT, Python)
  gRPC :50061
  ├─ Health()                → 卡片狀態、溫度、已載入模型、佇列長度
  ├─ Layout(image)           → [{type, bbox, score}]
  ├─ DetectText(image)       → [{bbox, score}]
  ├─ DetectTableSeal(image)  → [{type, bbox, score}]
  ├─ RedactFaces(image)      → image, [{bbox}]
  └─ Stream(camera_id)       → 事件流（走 DX-STREAM）
```

協調器把每個 RPC 包成同名 MCP 工具；`Health()` 回報異常時，這些工具標記為不可用，文件匯入流程退回純 CPU 版面分析（較慢但可用），LLM 主流程不受影響。

### A.6 部署前提（2026-11-08 已確認）

| 項目 | 狀態 | 結論 |
|---|---|---|
| DX-M1 規格與模型支援範圍 | 已確認 | 以 DeepX 公開型錄為準：視覺模型（YOLO、ViT、VLM 類）；BERT、Whisper、LLM 不列入 DX-M1 工作。實際安裝 SDK 後若模型庫新增文字或語音模型，走第 1.2 節驗證流程再評估 |
| M.2 插槽 | 已確認 | PCIe Gen3 x4 以上，不與 NVMe 共用頻寬 |
| INT8 校正資料 | 已確認 | 使用自己場域的掃描件與影像（建議 200～500 張），不沿用公開資料集的校正結果 |
| Linux 核心與 DX-RT 驅動相容性 | 安裝時確認 | 依實際安裝的 SDK 版本說明為準 |
